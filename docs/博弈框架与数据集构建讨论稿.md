## 一页结论

建议把项目拆成两条相互供数、但贡献边界清晰的论文线：

1. **检测与白盒解释论文（Paper A）**：回答“谁是协同欺骗账号、为什么这样判断、它在团伙中扮演什么角色”。核心是跨维检测与四维解释质量：预测保真、几何保真、角色保真、证据可追溯。
2. **闭环博弈与动态监测论文（Paper B）**：回答“攻击者在被监测和干预后如何适应，防御者应在何时、对谁、采取何种干预，才能以较低代价压制传播，同时给人类专家留下可复核证据”。核心不是“再换一个检测模型”，而是把现有开放环沙箱改造成可观测、可干预、可反事实评估的闭环安全博弈。

可信的创新叙事应建立在真实、可复现实验上，而不是“讲得唬人”。建议使用暂定名称：

> **TRACE-Game：面向协同欺骗的可追溯闭环攻防博弈框架**  
> Trajectory-aware, Role-aware, Attribution-grounded, Counterfactual, Expert-in-the-loop Game

主叙事是：平台并不能看到攻击者的隐藏提示词或私有协同，只能看到流式文本、行为和关系图；攻击者会在干预后改变节奏、角色和协作结构；防御者必须在延迟观测和预算约束下，用动态检测和白盒证据做连续决策。最终输出不是一个分数，而是供专家复核的“账号—角色—行为—传播链—模型依据—干预结果”证据包。

现稿同时把以下内容写进了 future work：**主动多智能体对抗、实时干预、流式双曲图引擎**。这正好为 Paper B 留出了清晰空间。

### 1.3 当前不能直接宣称已经完成的内容

- 当前可见的 72 人结果只有 1 timestep，不能证明“多轮动态博弈”；

- 现有框架仍有硬编码输出路径，尚未形成统一 run 目录；
- 当前检测更接近离线/周期性检测，尚未形成严格的逐 timestep 闭环；
- “八类角色”目前包含明显的事后语义命名，需要补角色保真验证；
- SHAP 说明的是模型归因，不等同于证据因果性；
- 数据规模脚本存在不等于规模实验已经跑通；
- 若对比表中的基线数字来自文献而非同一划分复跑，论文中必须明确来源。

## 2. 如何把原框架改造成自己的创新

### 2.1 原框架与新框架的本质差异

原框架主要回答：恶意智能体是否会形成协同行为，平台干预能否影响传播，LLM 能否从完整轨迹识别恶意账号。

新框架应回答：在部分可观测、检测延迟、干预预算与误伤成本同时存在时，攻击者与防御者如何连续适应；防御端如何把动态风险、角色变化和可追溯证据联合用于策略选择。

闭环为：

**环境演化 → 流式事件 → 动态检测 → 四维解释 → 防御决策 → 平台干预 → 攻击者适应 → 新一轮环境演化**

### 2.2 攻击端需要更真实

攻击者不再只有 good/bad 两类，而应至少包含以下状态：

- 潜伏者：低活跃、正常内容占比高，等待触发；
- 领导者：发布目标和任务，但降低直接扩散痕迹；
- 桥接者：跨社区传播；
- 放大者：点赞、转发、评论协同；
- 替补者：同伴被封禁后接管任务；
- 伪装者：根据风险反馈降低情绪异常、改变文风和节奏。

攻击策略至少有三个可控维度：

- 协同结构：中心化、去中心化、混合；
- 适应机制：无反思、自反思、共享反思；
- 规避机制：降频、角色轮换、边重连、内容改写、休眠后再激活。

### 2.3 防御端需要更真实

防御者不能使用攻击者私有提示、真实标签或完整未来轨迹。每轮只能读取截止当前时刻的平台可见事件，并受到：

- 观测延迟；
- 检测调用预算；
- 干预预算；
- 误伤成本；
- 专家复核容量；
- 不同干预的冷却时间和副作用；
- 模型漂移与攻击者适应。

动作空间可设为：

- 不动作；
- 进入观察名单；
- 降低推荐/限流；
- 添加事实核查或争议信息提示；
- 请求专家复核；
- 临时冻结；
- 封禁账号或切断团伙关键边。

### 2.4 四维解释如何进入闭环

- **预测保真**：解释选出的特征/事件能否重构或保持原预测；用 deletion/insertion、局部代理一致性或 top-k evidence sufficiency 衡量。
- **几何保真**：解释中的层级位置、邻居与传播链是否忠实于模型的双曲几何；用邻域保持率、层级次序一致性、距离相关性衡量。
- **角色保真**：角色名称是否对应可观察职责，而非仅给聚类贴标签；用已知合成真值、任务黑板真值、跨 seed 稳定性和角色互换检测衡量。
- **证据可追溯**：每条结论能否追溯到原始事件、时间、账号、内容、边、模型版本和干预；用 evidence coverage、provenance completeness、hash verification 衡量。

关键点：解释不是论文末尾的一张 SHAP 图，而是防御策略的输入，也是专家审计的交付物。

## 3. 仿真数据集的构建方案

### 3.1 数据集不是单个 DB，而是“场景—轨迹—证据—结果”包

每次运行应包含：

- `config_resolved.yaml`：展开后的全部参数；
- `run_manifest.json`：run_id、时间、代码提交、环境、模型、随机种子、输入哈希；
- `initial_agents.csv`：身份、角色真值、画像、初始社区、活动参数；
- `initial_graph.*`：初始关注和推荐关系；
- `events.jsonl`：逐事件时间、actor、action、target、content_id；
- `graph_snapshots/`：按 checkpoint 保存节点、边和属性；
- `task_blackboard_audit.json`：真实协同任务创建与承接；
- `detector_snapshots.jsonl`：每个检测时点的风险和预测；
- `explanations.jsonl`：四维解释与证据引用；
- `interventions.jsonl`：决策、原因、对象、成本、执行结果；
- `metrics_by_timestep.csv`：传播、检测、误伤、成本、角色变化；
- `final_metrics.json`：整轮汇总；
- `stdout.log`、`stderr.log`、资源占用和失败信息；
- `artifact_index.json`：所有文件路径、大小和 SHA-256。

### 3.2 人数与轮次

建议不要一开始把所有格子跑满。采用三级矩阵：

**开发集**

- N = 10、50、100；
- T = 5 做冒烟，T = 30 做完整技术验证；
- 每个条件 2 个 seed；
- 用途：排错、验证闭环、录制短演示。

**主实验集**

- N = 100、500、1000；
- T = 30 和 50 两组；
- 每个关键条件至少 5 个 seed；
- 这是论文统计检验的主体。

**扩展性集**

- N = 2000、5000；
- T = 30；
- 先跑 3 个 seed；
- 简化 LLM 调用：仅恶意/关键智能体使用高成本模型，其余使用缓存、规则或小模型；
- 用途：证明吞吐、存储、延迟与关键指标趋势，不承担全部机制结论。

不建议把“50 轮两组”解释为简单重复两遍。应明确为 T=30 与 T=50 两个时域设置；每个设置再用多个随机种子重复。

### 3.3 主实验因子

主效应优先保留五类：

- 协同：none / centralized / decentralized；
- 适应：off / reflection / shared reflection；
- 动态防御：none / static periodic / risk-triggered / explanation-guided；
- 干预：warning / downrank / debunk / ban（主文可选择 2—3 个）；
- 攻击比例：5% / 10% / 20%。

其余参数固定或放附录。全因子组合太大，建议先使用分阶段消融：

1. 固定 10% 攻击者，比较闭环防御；
2. 固定最佳防御，比较协同与适应；
3. 固定核心条件，比较规模和攻击比例；
4. 用消融验证解释是否真正改善防御决策。

### 3.4 1000 人推荐配置

推荐的第一版正式配置：

- 1000 人，其中 900 benign、100 deceptive；
- 4 个社区；
- 30 timestep 与 50 timestep；
- centralized 与 decentralized 两种协同；
- reflection/shared reflection 分开设置；
- 防御启动暖身期 5 timestep；
- 检测窗口 5 timestep，步长 1 或 5；
- 干预预算：每轮最多处理 1%、3%、5% 账号三档；
- detector threshold 不要只用 0.5，需用验证集选择并报告；
- 5 个 seed：42、43、44、45、46；
- temperature 主实验固定为 0 或较低值，稳健性实验再提高；
- 保存 t=0、5、10、15、20、25、30（以及 40、50）的图快照；
- 每轮结束保存原始事件，不能只保存 summary。

### 3.5 数据划分与泄漏防护

- 按 campaign 或 scenario 划分训练/验证/测试，不能把同一场景不同时间片随机打散；
- 画像模板、提示词模板和内容种子也要跨划分隔离；
- 同一账号的不同时间片不能同时出现在训练和测试；
- 合成数据的角色真值只能用于评测，不得进入在线防御器输入；
- 测试时隐藏任务黑板和私有协同信息，任务黑板只用于角色保真和追溯性评分；
- 每个拆分保存 ID 清单与哈希。

## 4. TwiBot-22 真实数据的使用方式

TwiBot-22 用于证明检测与解释能落到真实社交图上，不用于证明在线干预的真实因果效果，因为它不是平台在线随机实验。

建议分两阶段：

1. **立即完成访问与原始数据归档**。当前官方资料显示 TwiBot-22 是包含用户、推文、标签和图关系的大规模基准；完整数据应通过官方渠道获取，并遵守其研究用途和许可要求。
2. **框架跑通后做真实数据验证**。用现有动态适配器抽取 N=120、500、1000、5000 的固定子集；每个子集保存抽样 seed、core user ID、boundary node 规则、动作与关注截断参数。

适配器当前默认可控参数包括：

- `total_sample_size`；
- `max_actions=50`；
- `max_follows=100`；
- `random_seed=42`；
- 是否抓取 boundary profile。

需要补强：

- 输出 sampled core IDs 和 sampled bot IDs；
- 输出原始文件哈希与适配器代码提交；
- 记录丢失推文、缺失画像、截断比例；
- 保持一个固定 benchmark split，不要每次重新随机抽样；
- “TwiBot”拼写统一，避免代码中的 `twinbot` 与论文名混用造成复现困惑。

## 5. 评价指标

### 5.1 检测

- AUROC、AUPRC、F1、precision、recall；
- attack escape rate；
- time-to-detect；
- early-detection AUC；
- 按角色、规模、协同机制分层结果。

### 5.2 传播和干预

- 欺骗内容曝光量、传播深度、传播速度；
- 触达正常用户数；
- 团伙任务完成率；
- 干预前后相对下降；
- benign utility loss；
- false intervention rate；
- 单位收益成本与总干预预算。

### 5.3 动态适应

- 检测后降频幅度；
- 角色切换率；
- 网络重连率；
- 替补接管成功率；
- 攻防后悔值或累计效用；
- 跨窗口概念漂移。

### 5.4 四维解释

- 预测保真：top-k sufficiency、comprehensiveness、局部一致性；
- 几何保真：邻域保持、距离秩相关、层级顺序一致；
- 角色保真：与任务真值的 NMI/ARI/F1、跨 seed 稳定性；
- 可追溯：证据覆盖率、字段完整率、哈希校验通过率、人工复核一致率。

## 6. 必做对照和消融

- 原生 LLM detector；
- 旧的静态情感计算 + 网络角色分类；
- 动态检测但无解释参与决策；
- 动态检测 + SHAP；
- 动态检测 + 四维解释；
- 四维解释 + 专家/规则策略；
- oracle detector（性能上界，只用于分析）；
- 无防御与随机干预；
- 去掉心理特征、去掉双曲几何、去掉角色、去掉任务审计；
- static periodic 与 risk-triggered 的等预算比较。

最关键实验：

> 在相同干预预算与误伤约束下，解释引导的闭环防御是否比仅风险分数、静态周期检测和原生 LLM detector 更早发现关键角色，并更有效降低欺骗传播？

## 7. 结果保存与演示视频设计

统一目录：

`runs/{experiment_id}/{condition_id}/seed_{seed}/{run_id}/`

其中 `run_id` 建议为：

`YYYYMMDD-HHMMSS_N{N}_T{T}_{attack}_{defense}_s{seed}_{gitshort}`

运行原则：

- 原始数据只追加，不覆盖；
- summary 可重算；
- 所有图表必须能由原始事件重新生成；
- 每次运行先写 manifest，再启动模型；
- 每个 checkpoint 做原子保存；
- 失败运行也保存配置、日志和失败阶段；
- 大文件保存内容哈希，必要时只在 Git 中提交索引；
- 禁止把输出写到个人 Windows 盘符或未记录的临时目录。

演示视频脚本建议展示：

1. 初始网络与角色；
2. 欺骗任务在任务黑板上创建和被承接；
3. 风险随时间上升；
4. 解释定位领导者、桥接者与关键证据；
5. 防御动作执行；
6. 攻击者降频、换角或替补；
7. 干预前后的传播曲线与专家证据包。

5. 确认攻击者比例和主干预：建议 10% 攻击者，主文先比较 downrank/debunk/ban 中的两类。
6. 指定一个共享存储根目录，禁止个人路径；确定结果保留周期和备份位置。
7. 把 DS API 的调用限制、价格/额度和密钥配置方式告诉负责跑仿真的人；密钥不能写进 YAML 或 Git。

## 10. 第一次讨论会需要拍板的问题

1. Paper B 是偏安全、社交计算还是多智能体系统？目标 venue 决定写法和实验重点。
2. 防御策略由规则、强化学习、bandit 还是 LLM 决策？建议先以可复现的规则/bandit 做主方法，LLM 策略作为对照或扩展。
3. “实时”定义为每事件、每 timestep，还是每 5 timestep 窗口？建议先定义为 timestep 级流式更新。
4. 是否允许防御器使用文本大模型？建议允许，但设置调用预算并与轻量检测器等预算比较。
5. 1000 人场景的 LLM 覆盖范围？建议异构：关键攻击者与抽样正常用户调用 LLM，其余使用缓存/代理策略。
6. 人类专家实验是否来得及？最低可做 2—3 名领域人员的小规模证据包复核，并报告一致性与耗时。
7. 主张“四维解释首次提出”前必须做系统文献检索；当前只能写“我们提出四维评估框架”，不能未经检索直接使用“首次”。

## 11. 当前风险登记

- 时间风险：距截稿不足两个月；对策是先闭环、后规模，先核心矩阵、后扩展。
- 成本风险：1000×50 的全 LLM 调用可能不可承受；对策是异构代理、缓存和分层采样。
- 复现风险：当前存在硬编码路径与未统一输出；对策是 run schema 和 manifest 优先于大规模运行。
- 真实性风险：合成数据可能出现提示词标签泄漏；对策是模板隔离、跨场景划分和 adversarial paraphrase。
- 解释风险：SHAP 不等于因果证据；对策是反事实删除、角色真值和 provenance audit。
- 论文风险：两篇贡献重叠；对策是 Paper A 固定为检测/解释，Paper B 固定为闭环决策/动态适应。
- 真实数据风险：TwiBot-22 不能验证在线干预因果；对策是只用于外部有效性和解释展示。
